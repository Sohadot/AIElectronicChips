# IDE-010: Industrial Evidence Request & Research Workbench

- **Model:** [`data/industrial-evidence-requests.json`](data/industrial-evidence-requests.json). It has 3 workflows and 41 evidence requirements; scientific review is pending.
- **Public route:** `/research-workbench/`, generated by `scripts/render_research_workbench.py` between the `research-workbench` markers.
- **Script:** `assets/js/research-workbench.js`. It is local, deferred and progressive enhancement only.
- **Validator:** `scripts/validate_evidence_requests.py`, run by `validate_all.py`.
- **Tests:** `tests/test_research_workbench.py`.

## Why a dedicated route

The workbench adds functions that no reference page has: per-requirement collection statuses, local notes, JSON and CSV export, and a print view for one workflow. Folding these into `/sovereignty-stack/` would add form controls and a script to a page that is script-free, and would change the 25 pathway steps' surroundings. The new route is therefore separate. Contextual links lead to it from the following pages:

- `/sovereignty-stack/`: the "Read between layers" section and the related cards;
- `/hbm-memory/`: workflow A;
- `/interconnects/`: workflow B;
- `/ai-chip-infrastructure/`: workflow C.

No pathway step was changed.

## Workflows

| Workflow | Research question | Requirements |
| --- | --- | --- |
| A. HBM4 integration evidence request | What documentary evidence would be required to substantiate the integration and qualification of named HBM4 memory in a specific AI accelerator package? | 13 |
| B. Accelerator bandwidth comparison evidence request | What evidence is required before comparing memory and interconnect performance between two accelerator systems? | 13 |
| C. AI rack deployment evidence request | Which documentary records are necessary to move from a published AI rack specification to a defensible statement about installation, commissioning, and operation? | 15 |

Workflow B keeps each published figure in place and selects none of them:

- the 896 GB/s MI300X figure, whose per-GPU scope is unstated;
- the 22 and 19.2 TB/s Rubin memory figures;
- the 3.6 and 3 TB/s NVLink 6 figures.

The validator fails if any of these figures is dropped.

Workflow C lists requirements in stage order: Specified → Procured → Installed → Commissioned → Operationally observed, plus Access. Each requirement states that a record for one stage does not imply the next.

## Requirement fields

Each requirement records:

- the document to request and why it matters;
- the ontology layer and evidence category;
- its basis: source-derived, or this project's analytical recommendation;
- its public availability;
- its technical scope;
- its sources, findings, unresolved questions and conflict-register entries;
- a reference anchor;
- what to consider on receipt and its limitations;
- what it could support after expert review, and what it does not establish without that review.

The validator enforces the following rules:

- every source is active and cited by the requirement's own findings or conflict entries;
- every finding, question, conflict and anchor exists;
- an analytical recommendation cites no sources or findings;
- "published" or "partially published" needs the sources that publish it;
- no readiness, qualification, approval or comparative verdict language is used;
- the unverified 2025 AMD CDNA 4 edition (endnote MI350-007) appears nowhere as evidence;
- no unpublished Atlas candidate ID is used.

## Collection, export and privacy

The four statuses are Not requested, Requested, Document received (not reviewed) and Needs expert review. They record the researcher's own collection progress. The tool does not sum, score or turn them into a result. No status means "verified".

This website never submits, saves or writes to the URL anything entered, and never injects it as HTML. The note field turns off browser spelling and autocorrect services (`spellcheck="false"`, `autocorrect="off"`, `autocapitalize="off"`), because services such as Chrome's Enhanced Spell Check can send typed text to a third party. The page does not promise browser-wide privacy: other browser, extension or operating-system input features follow the user's own settings, and the privacy note says so. The validator rejects an enabled spell-check, a missing `spellcheck="false"` or `autocorrect="off"`, and unconditional privacy claims. The validator rejects all of the following in the script:

- `fetch`, `XMLHttpRequest`, `sendBeacon` and `WebSocket`;
- browser storage and cookies;
- history and location writes;
- `innerHTML` and `eval`.

Reloading the page clears the session.

Exports carry the disclaimer that the evidence "has not been independently validated". CSV cells are quoted, and any cell that starts with `=`, `+`, `-`, `@`, tab or carriage return is prefixed with `'` so spreadsheets do not run it as a formula.

## Browser test in CI

The validate job installs pinned Playwright 1.63.0 and headless Chromium outside the repository, then runs the regression suite and a named "Research workbench browser functional smoke test" step with `AEC_REQUIRE_BROWSER=1`. In that mode the browser test fails instead of skipping when Node or Playwright is missing. It checks:

- status controls and the note field, including spelling attributes on all 41 notes;
- JSON and CSV export content, including formula escaping and the disclaimer;
- the print view: one workflow, traces opened, restored afterwards;
- that another tab and a reload start from defaults, and that clearing works;
- no outbound or non-GET requests, empty browser storage and an unchanged URL.

A unit test fails if the workflow stops requiring the browser test.

## Fail-closed checks

`validate_all.py` fails in any of these cases:

- the model, the page or the script is missing;
- the page does not render every workflow, requirement and reference statically;
- the page loads any script other than the local deferred workbench script;
- the `<noscript>` explanation or the link to the data file is missing;
- the page is out of sync with the model.

## Boundaries

The workbench prepares evidence requests and is not an assessment. It does not state that the requested documents exist. It does not state that any product, supplier or site meets a requirement. It produces no readiness, qualification, compliance or ranking result. No reviewer, approval or scientific review is recorded. The Atlas still has no approved relationships.

## IDE-015: documentary preflight for Workflow C

- **Definitions:** [`data/deployment-evidence-preflight.json`](data/deployment-evidence-preflight.json). It contains the four selections, the significance and request wording for each of the 11 IDE-014 attributes, the ten evidence-state boundaries, and the packet label and disclaimers.
- **Record model:** reused unchanged from IDE-014 ([`rack-deployment-verification-dossier-014.json`](data/research/institutional/rack-deployment-verification-dossier-014.json)). This covers the 18 record types, their ceilings and required attributes, the category errors, the 12 dependencies and the 15-row claim-to-evidence matrix. The nine evidence states are Release 006's.
- **Where:** inside Workflow C on `/research-workbench/`, generated by `scripts/render_research_workbench.py`. There is no new route.
- **Validator:** `scripts/validate_deployment_preflight.py`, run by `validate_all.py`.
- **Tests:** `tests/test_deployment_preflight.py`, including a real-browser run of the hypothetical scenarios below.

### What it adds to IDE-010 and IDE-014

IDE-010 records whether a researcher has *requested or received* each document. IDE-014 says, in a research document, which kind of record can support which state. Neither lets a researcher check one document against the attributes it must carry. The preflight does that, for one Workflow C requirement at a time:

1. The researcher chooses a requirement: from the list, or with "Open documentary preflight" on any Workflow C requirement.
2. The page shows the claim and the record or records that should exist, who holds each, and the highest state each kind of record could support (its *ceiling*, an upper bound and not a state reached).
3. For each record, it shows the attributes the record must carry and what even a complete record does not establish.
4. It shows the documents that cannot substitute for the record, the category errors to avoid, and the documentary dependencies on other requirements.
5. The researcher marks the record as held, not held or unknown, and marks each attribute as present, missing or unknown. "Not yet marked" is the default and is kept apart from "unknown".
6. The gap explanation lists:
   - what is present, as the researcher reports it;
   - what is missing or unknown, and why it matters;
   - the next documentary request to each holder;
   - what is not yet marked;
   - the prohibited inference.
7. **Export preflight JSON**, **Export preflight CSV** and **Print preflight** produce a packet titled "Documentary Preflight — Not an Evidence Verification or Readiness Assessment". The packet carries the selections, outstanding requests, ceilings, dependencies, prohibited inferences, category errors, boundaries, methodology references, disclaimers, export date and format version.

### Boundaries

- The script holds no evidence-state name and computes no state. It copies each ceiling from the page, and every packet reports `evidence_state_established: null`. The validator rejects a script that names any of the eight supportable states.
- Marking every attribute present yields only: "ready only for substantive examination by a qualified human reviewer". No score, percentage, grade or colour is produced.
- A record type whose ceiling is below the claim's target state is marked as unable to support it on its own (for example, acceptance criteria for rc-12).
- Technical testing and formal acceptance are separate records (rc-12). Access records have no ceiling and never advance a deployment state (rc-15).
- Marking an upstream record present changes nothing in a dependent requirement. The browser test checks this for rc-06 → rc-10.

### Privacy

The preflight collects only radio selections. It has no free-text field, no upload and no identifier. It uses the same script and the same safeguards as the rest of the workbench: no transmission, storage, URL state or HTML interpolation, and CSV cells are quoted and protected against formulas. Reloading the page clears it.

### Publication

The preflight is published as clearly labelled research-preparation guidance, under the same rule as the reference pages that present Release 006 (ADR-020): it carries "Scientific review pending", the record model's compilation date, the AI-assisted status and no review claim. IDE-014's decision not to change `/ai-chip-infrastructure/` is untouched: the record model is not presented there as reference content. See ADR-022.
